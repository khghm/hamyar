# حساب‌های تست — موقتی

> ⚠️ **این پوشه موقتی است.** در `.gitignore` است و عمداً commit نمی‌شود.
> پس از تست، حذف کامل با یک دستور انجام می‌شود.

## چرا ایمیل و نه شمارهٔ موبایل

Supabase Auth با **ایمیل** کار می‌کند. ارائه‌دهندهٔ Phone روی این پروژه خاموش
است و برای روشن‌شدن به اعتبارنامهٔ یک شرکت پیامک (Twilio و…) نیاز دارد؛ Email از
قبل فعال است و هیچ اعتبارنامهٔ بیرونی نمی‌خواهد.

شمارهٔ موبایل همچنان ذخیره می‌شود — `profiles.phone` و `staff_accounts.phone` قید
`^09[0-9]{9}$` دارند — ولی دیگر کلید ورود نیست.

## ساخت

کلید `service_role` لازم است. آن را در `.env` پروژه بگذارید (فایل در
`.gitignore` است) — **بدون** پیشوند `VITE_`، وگرنه کلید به مرورگر می‌رود:

```
SUPABASE_SERVICE_ROLE_KEY=<کلید service_role>
```

از کجا: Supabase → Project Settings → API → `service_role`.

سپس:

```bash
node scripts/dev/test-accounts.mjs
```

اجرای دوباره بی‌خطر است: حساب‌های موجود را رد می‌کند و دوباره نمی‌سازد.

> پیش‌نیاز: مهاجرت‌ها و `seed.sql` باید روی پروژه اجرا شده باشند، وگرنه خطای
> «نقش … در دیتابیس نیست» می‌گیرید.

## حذف

```bash
node scripts/dev/test-accounts.mjs --remove
```

حذف کاربر از Supabase Auth به‌صورت آبشاری `profiles` و `staff_accounts` را هم
پاک می‌کند (هر دو `on delete cascade` دارند)، و نقش موقت `__TEST_VIEWER__` هم
حذف می‌شود. اگر چیزی ماند، ایمیل‌های فهرست‌شده در خروجی `--remove` را از
Supabase → Authentication → Users پاک کنید.

برای حذف کاملِ ابزار: `rm -r scripts/dev` و برداشتن دو خط از `.gitignore`.

## دو ابزار دیگر

**`db-query.mjs`** — اجرای SQL فقط-خواندنی روی پروژهٔ ابری، از طریق
Management API:

```bash
node scripts/dev/db-query.mjs "select count(*) from roles"
```

چرا Management API و نه اتصال مستقیم؟ سرور پروژه IPv6-only است
(`db.<ref>.supabase.co` فقط AAAA برمی‌گرداند) و ماشین‌های بدون IPv6 به پورت‌های
۵۴۳۲/۶۵۴۳/۶۵۴۴ دسترسی ندارند. Management API کوئری را سمت سرور اجرا می‌کند.
اسکریپت هر چیزی جز `SELECT`/`WITH`/`EXPLAIN` را رد می‌کند تا نتواند دیتابیس را
تغییر دهد.

**`verify-rls.mjs`** — بررسی سرتاسریِ تفکیک خواندن/نوشتن در RLS
(مهاجرت `015`)، با ورود واقعی از طریق Auth:

```bash
node scripts/dev/verify-rls.mjs
```

نکتهٔ مهم برای خواننده: **PostgREST مجوزهای RLS را با فیلتر کردن سطرها اعمال
می‌کند، نه با خطا.** یک `DELETE` که RLS مسدودش کند، `HTTP 200` با صفر سطر
برمی‌گرداند. پس تست نباید روی کد وضعیت تکیه کند — باید ثابت کند که سطر هنوز
سرِ جایش است. این اسکریپت دقیقاً همین کار را می‌کند.

## چه چیزی با `015` عوض شد

۲۰ سیاست با الگوی `for all using (مجوز_مشاهده or مجوز_ویرایش)` نوشته شده
بودند. `using` روی `DELETE` هم حاکم است و `DELETE` اصلاً `with check` ندارد،
پس کارمندی که فقط مجوز «مشاهده» داشت می‌توانست سطرها را حذف کند — از جمله
حذف حساب‌های کارمندی با `perm15`. حالا هر سیاست به چهار سیاست بر اساس *دستور*
تقسیم شده: `select` با مجوزِ مشاهده، و `insert`/`update`/`delete` با مجوزِ نوشتن.

## چه حساب‌هایی ساخته می‌شود

| ایمیل | شماره | نقش |
| --- | --- | --- |
| `admin.hamyar@example.com` | `09120000001` | مدیر کل (دسترسی کامل) |
| `staffSales.hamyar@example.com` | `09120000002` | مدیر فروش |
| `staffServices.hamyar@example.com` | `09120000003` | اپراتور خدمات |
| `staffSupport.hamyar@example.com` | `09120000004` | کارشناس پشتیبانی |
| `staffInviteViewer.hamyar@example.com` | `09120000005` | نقش موقت `__TEST_VIEWER__` — فقط `perm29` |
| `customer1…4.hamyar@example.com` | `09120000101`–`104` | مشتری |

رمز همه: `Test1234!` (با `TEST_ACCOUNTS_PASSWORD` قابل تغییر).

`staffInviteViewer` عمداً فقط `perm29` دارد تا بتوانید مطمئن شوید نوشتنِ تنظیمات
باشگاه مشتریان واقعاً به `perm43` بسته است: تب‌های «تنظیمات گیمیفیکیشن»، «سطوح و
طبقات»، «فروشگاه پاداش‌ها» و «نشان‌ها» نباید برایش نمایش داده شوند.

دامنهٔ `example.com` طبق RFC 2606 رزرو‌شده است و هرگز ایمیلی به آن نمی‌رسد.
حساب‌ها با `email_confirm: true` ساخته می‌شوند، پس اصلاً ایمیل تأیید فرستاده
نمی‌شود.
